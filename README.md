# Isochrone Map

A modern take on Francis Galton's 1881 travel-time map: how long does it
take to reach any point in the world from London, given the global
flight network, plus a rough estimate of the "last mile" by road or sea?

## Idea

Flight *routes* (which airports connect to which) change slowly — the
big hub structure of the network is fairly stable over time, even if
individual schedules and prices are not. So this project deliberately
mixes two data sources of very different age:

- an old (~2014) OpenFlights route dataset, used only for **network
  topology** (who flies where),
- a current airport reference database, used for **coordinates**.

Flight time per route is *estimated* from great-circle distance (a rule
of thumb, not real schedules), and the fastest path from London to
every other airport is computed with Dijkstra's algorithm, including a
fixed per-connection transfer penalty. That gives every *airport* a
travel time. To turn that into a full world map, a global
[H3](https://h3geo.org/) hex grid is laid over the planet, and every
cell — land or water — is assigned the travel time of whichever
airport or port serves it fastest, including the "last mile" from that
hub to the cell itself (by road or by sea).

## Scripts

Each step is a separate module so individual pieces (e.g. the transfer
time penalty, or the flight-time formula) can be tuned without touching
the rest.

| File | Responsibility |
|---|---|
| `config.py` | All tunable constants in one place: file paths, London origin airports, flight-time formula constants, transfer time, ground/sea speed, H3 resolution, search radii, plot colormap and color cap. |
| `distance.py` | Great-circle distance between two coordinates (haversine) — `haversine_miles` (scalar) for flight-time estimation, `haversine_km_vec` (numpy-vectorized) for `friction_map_from_point.py`'s `--heli`/`--jetpack` distance-to-every-airport calculation. |
| `flight_time.py` | Rule-of-thumb flight time from distance: 30 minutes base + 1 hour per 500 miles. |
| `data_loading.py` | Reads and cleans `routes.csv` / `airports.csv`; filters to airports with a valid 3-letter IATA code and coordinates. |
| `ports_loading.py` | Reads `ports_corrected.csv` (already lon/lat-corrected, see `fix_ports_coordinates.py`) and returns the columns the rest of the pipeline needs. Deliberately thin — no `reverse_geocoder`/`pycountry` import here, so it carries no native-extension baggage. |
| `fix_ports_coordinates.py` | One-time correction script (not part of the normal pipeline): reads the raw `ports.csv`, drops rows with missing coordinates, and fixes the many rows with longitude/latitude swapped — inconsistently (some rows are fine, some aren't, no reliable pattern by value range) — detected by reverse-geocoding both possible readings of each coordinate (`reverse_geocoder`, offline) and keeping whichever one's country matches the `Country` column (`pycountry` name → ISO code, with a small override table for spellings pycountry doesn't recognize), then writes `ports_corrected.csv`. Since `ports.csv` is a static dataset that never changes, there's no reason to redo this reverse-geocoding pass on every pipeline run — run it once, commit the result, done. This also gets `reverse-geocoder` (which pulls in `cykhash`, a native Cython extension with no Windows wheel for many Python versions, requiring a working MSVC toolchain to build from source — see MEMO.md) out of the required install path entirely: it's a `[dev-packages]` entry now, only needed if you ever have to rerun this script (e.g. `ports.csv` gets updated from upstream). |
| `graph_builder.py` | Builds a directed `networkx` graph: nodes are airports, edges are direct routes weighted by estimated flight time only (no transfer time yet). |
| `travel_time.py` | Runs Dijkstra from a virtual node connected to all London airports (LHR, LGW, LCY, STN, LTN) with zero cost, so the fastest departure airport is picked automatically. Transfer time per stop is added here, not baked into the graph, so it can be changed without rebuilding the graph. `compute_shortest_times`'s origin argument can also be a `{iata: entry_hours}` dict instead of a plain list — each virtual-node edge then gets that airport's individual entry cost instead of a flat 0.0, which is how `friction_map_from_point.py` feeds in the ground time from an arbitrary starting point to each candidate departure airport. |
| `main.py` | Orchestrates the pipeline above and writes `travel_times.csv`. |
| `plot_map.py` | Reads `travel_times.csv` and plots a world point map (Cartopy/Robinson projection), airports colored by travel time from London. |
| `h3_grid.py` | Builds a global H3 grid at a given resolution (all children of the 122 resolution-0 base cells). |
| `land_mask.py` | Classifies H3 cell centers as land or water (`global-land-mask`), so ground transport is only ever estimated where a road could plausibly exist. |
| `nearest_hub.py` | Two things: (1) `assign_travel_times` — for each grid cell, finds all hubs (airports or ports) within a search radius (haversine `BallTree`) and picks the one minimizing **total** time = the hub's own travel time from London + estimated last-mile time from the hub to the cell (ground speed for airports, sea speed for ports). Neither "nearest hub" nor "fastest hub from London" alone is correct — a farther but better-connected hub can win despite the longer last mile, and vice versa. Hubs that are themselves unreachable (`NaN` travel time) are dropped before the search, since `numpy.argmin` would otherwise silently propagate `NaN` into every result that considers them. (2) `nearest_value` — plain nearest-neighbor lookup, no hub logic, used to give each port the travel time of its nearest land cell. |
| `main_h3.py` | Splits the H3 grid into land and water cells via `land_mask.py`. Land cells get assigned via `nearest_hub.assign_travel_times` against airports. Each port then simply gets the travel time of its nearest already-computed land cell (`nearest_hub.nearest_value`) — a port isn't a separate transport mode with its own airport search, it's just a point on land that happens to also serve ships (writes `ports_travel_times.csv`). Water cells are then assigned via `nearest_hub.assign_travel_times` against those port times. Writes the combined `h3_travel_times.csv`. Takes `-r`/`--resolution` (default `config.H3_RESOLUTION`) — every other script that builds an H3 grid (`map_from_airport.py`, `friction_surface_map.py`, `friction_map_from_point.py`) does too. Output filenames get a `_resN` suffix whenever a non-default resolution is used, so different resolutions don't clobber each other; `plot_h3_map.py` reads the resolution back out of the data (`h3.get_resolution`) for its title instead of trusting `config.py`, which could be stale. |
| `plot_h3_map.py` | Reads `h3_travel_times.csv` and draws the filled hex grid on the Robinson map, plus small colored dots for every airport and port (orange/magenta) so you can see which hub is driving a region's color — off by default (`--airports`/`--ports`, or `show_airports=True`/`show_ports=True`, turn each on independently). Was a single combined `--no-hubs` opt-out defaulting to shown; flipped to opt-in and split in two because plotting every airport as an identical dot is misleading when many of them (e.g. tiny Arctic strips with zero scheduled routes in `routes.csv`) contribute no actual travel-time value at all. The color scale is capped at `COLOR_CAP_HOURS` — cells beyond that get the darkest color instead of stretching the whole scale, the same way Galton's original used discrete bands with a final "and beyond" category instead of a continuous gradient out to the true (multi-day, mid-ocean) maximum. Cells whose H3 boundary genuinely spans most of the globe (i.e. cells sitting at a pole, where all meridians converge) are dropped rather than "fixed" — treating that as an antimeridian crossing would balloon them into a giant polygon covering much of the map. Telling a true pole cell apart from an ordinary small cell that merely straddles the antimeridian (vertices just either side of ±180°, e.g. -179.9° and 179.9°) can't be done from longitude span alone: naive `max(lons) - min(lons)` gives ~358-360° for both cases, since crossing the dateline looks identical to spanning the globe once longitude isn't wrap-aware. `POLE_LAT_THRESHOLD_DEG` uses *latitude* instead — a real pole cell has boundary latitudes past 80° even at H3's coarsest resolution, an antimeridian cell has perfectly ordinary latitudes anywhere on Earth. Antimeridian cells aren't just shifted into view, though: an earlier attempt (add 360° to a cell's negative longitudes so it renders on the correct side) silently broke, because cartopy's Mercator `transform_points()` wraps any longitude past ±180° straight back into the standard range (181° projects identically to -179°) — the shift had no effect at the actual projection step, leaving one vertex of the hexagon on the opposite side of the map from its five siblings, and with `antialiased=False` that scan-converts as a solid horizontal band across most of the map at that cell's latitude (see MEMO.md, Phase 14zZg for the failure analysis). The working fix (Phase 14zZh) clips the polygon at the antimeridian into two real pieces instead: unwrap the cell (shift negative longitudes by +360° so all vertices form one contiguous polygon slightly past 180°), then cut that shape with a small Sutherland-Hodgman clip (`_clip_polygon_x()`) along the line lon=180° — the east piece is already within range and needs no further change, the west piece gets shifted back by -360° after clipping, landing it safely within ±180° too. Both pieces get the origin cell's `reisezeit_stunden` value; `plot_h3_map()` duplicates it accordingly, same as it briefly did for the broken vertex-shift version. Since every emitted vertex now stays strictly inside the projectable range, cartopy's wraparound never gets a chance to misplace anything. `origin_label` parameter controls the title/legend text, so the same function serves both the London map and `map_from_airport.py`. Output resolution is `--dpi` (or `dpi=`), default `config.MAP_DPI` — roughly quadruples in file size/render time each time you double it. On its own, though, `--dpi` doesn't define an actual physical size — the underlying figure is a fixed, essentially arbitrary `figsize=(16, 9)` canvas trimmed tightly around whatever content is rendered (`bbox_inches="tight"`), so "dots per inch" doesn't correspond to any real medium. `--paper` (a name from `config.PAPER_SIZES_IN` — `a0`-`a6`, `letter`, `legal`, `tabloid` — or custom centimeters as `BREITExHOEHE`, e.g. `50x60`, since poster print shops routinely don't offer DIN sizes at all; parsed/validated once by `parse_paper()`, shared across all four scripts the same way `parse_lat_limits()` already was) fixes that: `_apply_paper_size()` runs after `fig.savefig()`, scales the already tightly-cropped PNG to the full width of the chosen page in landscape (our maps are always wider than tall; DIN/US paper is much less so, ~1.41:1 for A-series vs. our ~1.6-1.8:1), and pastes it centered onto a page-sized canvas filled with `BACKGROUND_COLOR`, leaving equal blank margins top and bottom rather than distorting or cropping the map to fit the page's aspect ratio — deliberately left empty for now rather than auto-filled, as a natural spot for a future large headline. Pure raster post-processing (PIL, like `_apply_retro_noise`) rather than reworking the existing `figsize`/`bbox_inches="tight"` layout logic, which already auto-adapts to whatever combination of title/legend/explanation-box/frame elements is present regardless of flags — reproducing that adaptivity via a fixed physical-page `figsize` instead would mean abandoning the auto-crop and manually budgeting margins for every element. Runs *before* `_apply_retro_noise` when both are active, so the aged-paper grain also covers the newly added blank margins instead of leaving them looking unnaturally flat. Without `--paper`, behavior is unchanged (tight crop, no margins). `--galton` switches to Galton's original look: fixed-width discrete color bands instead of the continuous colormap, drawn as smooth `contourf` regions instead of individually colored hexagons. This is a rendering-only effect — the underlying CSV is untouched. Averaging over H3 neighbors turned out too locally-scoped to produce clean rings in noisy terrain (Sahara, Amazon interior) — the band edges just traced the noise one hex-width at a time. Instead, `_build_galton_grid()` interpolates the hex values onto a regular lat/lon raster (`GALTON_GRID_DEG`) and runs a real Gaussian blur (`GALTON_SIGMA_DEG`, `scipy.ndimage.gaussian_filter`) — land and water smoothed separately via `_nan_gaussian_filter()` so the coastline doesn't blur away — before `contourf` traces the band boundaries on that smoothed field. The land/water split itself comes from `global_land_mask`'s `globe.is_land()`, evaluated once per raster pixel — and that raw per-pixel classification turned out to be visibly speckled in places rather than following a clean coastline (confirmed by printing the boolean grid directly: isolated "land" pixels in open water and vice versa), most noticeably over small, glaciated Arctic archipelagos like Svalbard, producing a fringed/frayed patch of the wrong channel's color right inside those islands instead of a uniform fill — not a data-coverage gap, since the underlying H3 tiles were all correctly covered there. Since this mask only decides which of the two *smoothing channels* a raster cell's value falls into (the coastline actually drawn on the map is unrelated, always the accurate Natural Earth vector data), it's safe to clean up: `is_land_grid` itself is now run through `_nan_gaussian_filter()` at the same `GALTON_SIGMA_DEG` radius used for the values and re-thresholded at 0.5, smoothing away the single-pixel misclassifications before they ever reach the land/water split, with no effect on the drawn coastline shape. Also faster than the hex-neighbor approach despite doing more: a small raster + vectorized blur beats a Python loop over hundreds of thousands of hexagons. `--max-hours` overrides `GALTON_MAX_HOURS` (the color scale's total span in hours, only affects `--galton` mode — the darkest color is reached exactly at this value instead of at the fixed `COLOR_CAP_HOURS`), split evenly into as many bands as the active palette has colors (ten for `--cmap galton`, five for `--cmap galton5`, ten as a generic fallback for any other colormap name under `--galton`); `--cmap` overrides `COLORMAP` (any matplotlib colormap name, e.g. `plasma_r`, `inferno_r`, `magma_r`, `cividis_r` — all perceptually uniform like the default `viridis_r`) and applies in both modes. `--cmap galton` and `--cmap galton5` are special cases: `GALTON_COLORS`/`GALTON5_COLORS` are used to build a `ListedColormap` instead of looking up a matplotlib name — fixed, non-interpolated swatch colors read directly off the 1881 chart by the user rather than estimated, ten RGB values in dark/light pairs for each of the five hues (green → yellow → pink → blue → brown) for `galton`, one representative shade per hue for `galton5` (the actual single-swatch color from the original's own legend, not just "every other" of the ten — dark green, but *light* yellow/pink/blue/brown). Only the color mood is borrowed, not the original's 10-day band width — Galton's "within 10 days" category alone would cover this project's entire world (max ~48h), since travel got that much faster in 140 years. All four map-generating scripts take `--max-hours`/`--cmap`. `--galton` implies `--cmap galton` when `--cmap` isn't given explicitly (same "apply once inside `plot_h3_map()`, mirror in each calling script's `main()` before the filename is built" pattern as the `--rivers`/`--grid` implication below) — the retro look should default to Galton's actual colors, not `viridis_r`. `--labels` adds continent names (`CONTINENT_LABELS`, seven fixed hand-placed positions — these never change, so no need to derive them from a dataset, drawn bold via `CONTINENT_FONT`) and the world's most prominent cities (Natural Earth's `populated_places` layer, filtered to `SCALERANK <= CITY_LABEL_MAX_SCALERANK`, ~27 cities at the default of 0 — real city names with a genuine importance ranking, unlike our airport data, where the `name` field is an airport name like "Heathrow" rather than "London" and there's no ranking at all — drawn italic via `CITY_FONT`). City labels are then run through `adjust_text()` (the `adjustText` package) so overlapping ones in dense regions (e.g. Rio/São Paulo) repel each other into non-overlapping positions — city labels only, against each other, not against coastlines or the continent labels; `adjust_text()` reads each `Text`'s own transform (all city labels share `ccrs.PlateCarree()`), so it works correctly under both Mercator and Robinson without extra handling. Coastlines and all label text use `ANTHRACITE` (`#2b2e33`) rather than gray/black, and labels no longer get a white outline stroke — closer to the crisp, dark linework of the printed 1881 original. Typography: the title is set in Playfair Display Bold (`fonts/PlayfairDisplay-Bold.ttf`, a Google Font under the OFL license — matplotlib can't address a variable font's weight axis, so this is a static Bold instance produced once with `fonttools varLib.instancer`, not the variable file itself); continents are bold Libre Baskerville, cities italic Libre Baskerville (`fonts/LibreBaskerville-Bold.ttf`/`fonts/LibreBaskerville-Italic.ttf`, same OFL license, same static-instance treatment — instantiated from Google's variable `LibreBaskerville[wght].ttf`/`LibreBaskerville-Italic[wght].ttf` at weight 700/400 respectively). Originally this used real Baskerville via matplotlib's `family="Baskerville"`, which only resolves on macOS (where it ships as a system font) — anyone running the script elsewhere silently got whatever generic serif matplotlib fell back to. Libre Baskerville is a free, OFL-licensed revival designed as a substitute for the (non-free) original, so it's bundled in the repo like Playfair Display and looks the same on every platform. Font file paths, fallback family names, and font/marker sizes all live in `config.py` (`PLAYFAIR_BOLD_PATH`, `TITLE_FONT_FALLBACK_FAMILY`, `CONTINENT_FONT_PATH`, `CITY_FONT_PATH`, `CONTINENT_FONT_FALLBACK_FAMILY`, `CITY_FONT_FALLBACK_FAMILY`, `TITLE_FONT_SIZE`, `CONTINENT_FONT_SIZE`, `CITY_FONT_SIZE`, `CITY_MARKER_SIZE`) rather than as literals scattered across `ax.text()`/`ax.set_title()` calls, so the look can be tuned without touching the rendering code; if a font file is ever missing, each falls back to a generic `serif` family rather than erroring. Avoid Greek letters or other glyphs a display font might not cover in title text — Playfair Display has no `σ`, which silently renders as a tofu box instead of erroring. **Projection**: Mercator is the default (matching Galton's original, and the reason Greenland/Antarctica look oversized — a real Mercator distortion, not a bug), clipped to Galton's own asymmetric 80°N/60°S crop (Mercator can't represent the poles at all — infinite distance — and this default also cuts off most of the heavily-distorted, not very informative Antarctica) rather than a generic symmetric range; used regardless of `--galton`, not just as a retro-look detail. Pass `--robinson` for the earlier equal-area-ish Robinson projection instead. `--grid` draws a longitude/latitude graticule every 20° (`GRID_STEP_DEG`) via `ax.gridlines()`, in the same anthracite color and line width (`COASTLINE_LINEWIDTH`) as the coastlines (at 80% opacity, like the airport/port dots, so it stays subtle), so it reads as part of the same linework rather than a separate technical overlay. Latitude lines are centered on the equator rather than the poles: `ylocs=range(-90, 91, GRID_STEP_DEG)` looks equivalent to the longitude case (`xlocs=range(-180, 181, GRID_STEP_DEG)`) but isn't — 180 is a multiple of 20, so `xlocs` naturally lands on 0°, while 90 isn't a multiple of 20, so `range(-90, 91, 20)` starts at -90 and steps land on -90, -70, -50, ..., 10, 30, ..., 90, skipping the equator entirely. Fixed by counting outward from 0° instead: `lat_max = (90 // GRID_STEP_DEG) * GRID_STEP_DEG` (the largest multiple of `GRID_STEP_DEG` at or below 90°), then `ylocs=range(-lat_max, lat_max + 1, GRID_STEP_DEG)` — symmetric around the equator by construction, for any step size, not just the current 20°. Under `--galton`, two more of the original's frame elements appear regardless of `--grid`: bare-number degree labels on all four sides (cartopy's gridliner `draw_labels` with a `FuncFormatter` stripping the default °/N/E/S/W suffix, only supported for rectangular projections — so this is skipped under `--robinson`) and three border lines around the map, matching the original: a thin double rule directly at the map edge, plus a visibly heavier single outer rule (`FRAME_LINEWIDTH`, vs. `COASTLINE_LINEWIDTH` for the rest of the linework) further out that also encloses the degree-label text. The two thin rules are the existing "geo" spine (right at the map's own edge) plus a second `Rectangle` just inside it, `FRAME_GAP_PT` apart — the original tight double ruling directly around the map. The thick outer rule is a third `Rectangle`, positioned far enough out to enclose the gridliner's degree labels too, not just the bare map, matching how the original's frame encloses its axis numbers rather than leaving them to float outside the border. Since label text extent depends on font/size/DPI in ways that aren't known in advance, this outer rectangle's position comes from the union of the axes' own pixel bounding box and every gridliner label artist's `get_window_extent()` (`gl.label_artists`, empty under `--robinson` since labels aren't drawn there — the rectangle then just hugs the axes with a `FRAME_GAP_PT` margin, same as the inner double rule), plus `FRAME_GAP_PT` of breathing room beyond that — all gaps computed in points rather than as a fixed fraction of `ax.transAxes`, since the map isn't square and a fractional inset would leave visibly different horizontal/vertical gaps. The outer rectangle needs `clip_on=False`, since it legitimately extends outside the axes' own `[0, 1]` bounding box to reach around the labels. Right below that outer frame, two small italic credit lines — "O. Not exposed as CLI flags since they're a fixed part of the look, not something to tune per-map. `RETRO_SKETCH_SCALE`/`_LENGTH` are pixels, not points, despite the old comment saying otherwise — confirmed straight from matplotlib's own `set_sketch_params()` docstring — and pixels only mean a fixed physical size at one specific DPI, the one they were calibrated against (`config.MAP_DPI`, 150). Reverses the direction of the friction-surface Dijkstra: instead of spreading ground time out from every airport (its own travel time from London is already known), a single Dijkstra runs *from* the chosen point across the same cached land graph *to* every airport pixel, giving that airport's individual ground time from the point. Those (no longer uniform) ground times become the virtual-origin edge weights in `travel_time.compute_shortest_times`, so the normal flight-network Dijkstra folds "ground time to the airport" and "flight + transfer time" into one shortest-path run — same super-source trick used everywhere else in this project, just with the source and sink roles swapped relative to `friction_surface_global.py`. Passing both flags together (or `--james-bond` as shorthand for `--heli --jetpack`) chains them: heli for the first `HELI_RANGE_KM`, jetpack for up to another `JETPACK_RANGE_KM` beyond that. `-v`/`--verbose` (this script only) prints a one-time config overview before any work starts (origin, resolution/dpi, projection, `--galton` settings, active overlays, heli/jetpack speeds/ranges) plus a progress message before each major step (loading data, the combo-Dijkstra, spreading ground time to land cells, building sea cells, writing the CSVs, drawing the map) — without it, the script stays as quiet as before (just the friction-graph Dijkstra timing and the final "Karte gespeichert unter" line, both unconditional and unrelated to this flag).

Naively taking `min(ground_time_from_origin, air_time)` per destination is wrong, though — it either uses the friction graph for the *entire* trip or air travel for the *entire* trip, with no way to combine them, so it silently discards the flight distance the moment the destination is even slightly outside heli/jetpack range and forces the whole remaining trip to be walked from the origin (not from the edge of the flight range). `_combo_ground_minutes()` fixes this properly, reusing the same virtual-super-source Dijkstra trick used throughout this project (e.g. `friction_surface_global.py`'s airport-seeded world Dijkstra): every friction-graph node within air range gets a virtual edge from the origin weighted by *that node's own* `_air_hours_to()` value, then a single Dijkstra over the whole land graph gives, for every point in the world, the minimum over all reachable "landing spots" of (flight time to that spot + ground time from there onward) — genuinely "fly as far as is worthwhile, then walk the rest," radially symmetric around the flight-range circle instead of only showing up in whichever direction happened to make pure at-the-origin walking competitive. The origin itself is always a zero-cost landing spot, so this single function also covers plain walking with no flight at all — no special-casing needed for runs without `--heli`/`--jetpack`. `build_travel_times_from_point()` uses its result directly as each airport's entry time (replacing the old separate `min(ground, air)` computation entirely), and `_apply_combo_ground_to_h3()` applies the same array to every H3 land tile. `_apply_air_reach_to_h3()` (pure air time, no walking) still runs separately and additionally, since it's the only thing that can color H3 *sea* tiles — the friction graph is land-only. `air_suffix` (`_heli`/`_jetpack`/`_bond`) is threaded through every output filename, including the CSVs (not just the PNG) — otherwise a `--heli` run's `travel_times_from_<slug>.csv` would silently overwrite the plain run's, the same class of collision fixed earlier for `--cmap galton`/`galton5`. |

## Running it

```bash
pipenv install
pipenv run python main.py                 # -> travel_times.csv
pipenv run python plot_map.py             # -> travel_times_map_london_airports_points.png
pipenv run python main_h3.py              # -> h3_travel_times.csv, ports_travel_times.csv
pipenv run python plot_h3_map.py          # -> h3_travel_times_map_london_h3_land_and_sea.png
pipenv run python map_from_airport.py BVI # -> same outputs, from Birdsville instead of London
```

If Cartopy fails to download coastline data with an SSL error (a known
issue with some macOS Python installs), `plot_map.py` and
`plot_h3_map.py` already point it at the `certifi` certificate bundle
instead of the system store.

For `friction_surface_demo.py`, first download the road network extract
(not committed, ~196 MB):

```bash
mkdir -p osm_data
curl -L -o osm_data/queensland-latest.osm.pbf \
  https://download.geofabrik.de/australia-oceania/australia/queensland-latest.osm.pbf
pipenv run python friction_surface_demo.py
```

The Overpass API (which the more common `osmnx.graph_from_point()`
approach uses to fetch road data on demand) was unreachable from this
project's dev environment — direct HTTPS downloads worked fine, live
Overpass queries didn't (connection refused / 406, even via `curl`, on
multiple mirrors). That's why this script reads a pre-downloaded
Geofabrik `.osm.pbf` extract via `pyrosm` instead of querying Overpass
live; worth trying `osmnx` directly first in an environment where
Overpass is reachable.

For the global anisotropic map (`friction_surface_global.py` /
`friction_surface_map.py`), download the friction surface first
(not committed, ~744 MB unzipped):

```bash
mkdir -p friction_data
curl -L -o friction_data/friction_surface.zip \
  "https://data.malariaatlas.org/geoserver/ows?service=CSW&version=2.0.1&request=DirectDownload&ResourceId=Explorer:2020_motorized_friction_surface"
unzip -o friction_data/friction_surface.zip -d friction_data
pipenv run python friction_surface_global.py  # ~1-2 minutes, caches intermediate results
pipenv run python friction_surface_map.py     # -> h3_travel_times_map_london_friction_surface_land.png
```

## Known simplifications

- Flight time is a distance-based estimate, not real schedule data.
- Transfer time is a flat 1.5h penalty per stop, regardless of airport.
- The main pipeline's (`main_h3.py`) ground transport from an airport to
  a non-airport cell is a flat `GROUND_SPEED_KMH` (80 km/h) straight-line
  estimate — no roads, no terrain, no border crossings. It's *isotropic*:
  the model assumes you can travel equally fast in every direction from
  an airport, when real ground transport obviously follows roads/rail
  (compare the historical
  [Melbourne 1920s tram/rail isochrone map](https://en.wikipedia.org/wiki/Isochrone_map)
  that inspired this observation). Two separate scripts demonstrate the
  anisotropic alternative instead of changing the main pipeline outright
  (see `MEMO.md` for why they stayed separate):
  - `friction_surface_demo.py` — one region (Birdsville, Australia)
    using a real OpenStreetMap road network.
  - `friction_surface_global.py` / `friction_surface_map.py` — the whole
    world, using a pre-computed friction raster (Malaria Atlas Project)
    and a cost-distance graph instead of live routing. Doesn't cover
    Antarctica (the raster stops at 60°S) — those cells fall back to
    whatever the nearest available friction-graph node happens to be,
    which is visibly wrong the same way the isotropic model's Antarctica
    values were.
- Sea transport from a port to a water cell is likewise a flat
  `SEA_SPEED_KMH` (35 km/h) straight-line estimate with an effectively
  unlimited search radius, so every water cell gets a value even deep
  in the open ocean, far from the 333 ports in `ports.csv`. That's
  intentional (see MEMO.md) — the color cap in `plot_h3_map.py` is what
  keeps those multi-day mid-ocean values from swamping the map. The
  friction-surface map keeps this same sea model unchanged; only land
  cells get the anisotropic treatment.
- `ports.csv` covers only 333 major ports (an academic benchmark
  dataset), not an exhaustive port registry.
- The route network is ~10 years old; it's used only for topology, on
  the assumption that major hub connections don't disappear quickly.
