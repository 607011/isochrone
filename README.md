# Isochrone Map

A modern take on Francis Galton's 1881 travel-time map: how long does it
take to reach any point in the world from London, given the global
flight network, plus a rough estimate of the "last mile" by road or sea?

## Idea

Flight *routes* (which airports connect to which) change slowly — the
big hub structure of the network is fairly stable over time, even if
individual schedules and prices are not. So this project deliberately
mixes two data sources of very different age:

- an old (~2014) OpenFlights route dataset, used only for **network
  topology** (who flies where),
- a current airport reference database, used for **coordinates**.

Flight time per route is *estimated* from great-circle distance (a rule
of thumb, not real schedules), and the fastest path from London to
every other airport is computed with Dijkstra's algorithm, including a
fixed per-connection transfer penalty. That gives every *airport* a
travel time. To turn that into a full world map, a global
[H3](https://h3geo.org/) hex grid is laid over the planet, and every
cell — land or water — is assigned the travel time of whichever
airport or port serves it fastest, including the "last mile" from that
hub to the cell itself (by road or by sea).

## Data files

| File | Source | Format | Used for |
|---|---|---|---|
| `routes.csv` | OpenFlights `routes.dat` (~2014) | CSV with header: `Airline, Airline ID, Source airport, Source airport ID, Destination airport, Destination airport ID, Codeshare, Stops, Equipment` | which airports are directly connected |
| `airports.csv` | OpenFlights airport database | CSV, **no header**, 14 columns: `Airport ID, Name, City, Country, IATA, ICAO, Latitude, Longitude, Altitude, Timezone, DST, Tz database timezone, Type, Source` | airport coordinates, names, IATA filtering |
| `ports.csv` | [LINERLIB](https://github.com/blof/LINERLIB) (academic liner-shipping benchmark data) | Tab-separated: `UNLocode, name, Country, Cabotage_Region, D_Region, Longitude, Latitude, Draft, ...` | port coordinates. Only the positions are used, not LINERLIB's shipping-route/cost data — see MEMO.md for why routes between ports turned out to be unnecessary. |
| `travel_times.csv` | generated by `main.py` | CSV: `iata_code, name, lat, lon, reisezeit_stunden, anzahl_umstiege` | result of the shortest-path computation, one row per airport |
| `travel_times_map.png` | generated by `plot_map.py` | PNG | point map of the result |
| `ports_travel_times.csv` | generated by `main_h3.py` | CSV: `unlocode, name, Country, lat, lon, reisezeit_stunden` | each port's own travel time from London — simply copied from its nearest land H3 cell, see MEMO.md |
| `h3_travel_times.csv` | generated by `main_h3.py` | CSV: `h3_index, lat, lon, reisezeit_stunden, letzte_meile_stunden, hub_id, num_hubs_in_radius, hub_type` | travel time per H3 grid cell, land and water combined |
| `h3_travel_times_map.png` | generated by `plot_h3_map.py` | PNG | filled hex-grid map of the result |

Note: despite the filename and the `"OurAirports"` value in its last
column, `airports.csv` is in the classic OpenFlights format, not the
OurAirports CSV export (which has a different schema). The scripts
parse it accordingly — see [MEMO.md](MEMO.md) for how this was
clarified.

## Scripts

Each step is a separate module so individual pieces (e.g. the transfer
time penalty, or the flight-time formula) can be tuned without touching
the rest.

| File | Responsibility |
|---|---|
| `config.py` | All tunable constants in one place: file paths, London origin airports, flight-time formula constants, transfer time, ground/sea speed, H3 resolution, search radii, plot colormap and color cap. |
| `distance.py` | Great-circle distance between two coordinates (haversine). |
| `flight_time.py` | Rule-of-thumb flight time from distance: 30 minutes base + 1 hour per 500 miles. |
| `data_loading.py` | Reads and cleans `routes.csv` / `airports.csv`; filters to airports with a valid 3-letter IATA code and coordinates. |
| `ports_loading.py` | Reads and cleans `ports.csv`; drops rows with missing coordinates. Many rows have longitude/latitude swapped, inconsistently (some rows are fine, some aren't, with no reliable pattern by value range) — detected by reverse-geocoding both possible readings of each coordinate (`reverse_geocoder`, offline) and keeping whichever one's country matches the `Country` column (`pycountry` name → ISO code, with a small override table for spellings pycountry doesn't recognize). |
| `graph_builder.py` | Builds a directed `networkx` graph: nodes are airports, edges are direct routes weighted by estimated flight time only (no transfer time yet). |
| `travel_time.py` | Runs Dijkstra from a virtual node connected to all London airports (LHR, LGW, LCY, STN, LTN) with zero cost, so the fastest departure airport is picked automatically. Transfer time per stop is added here, not baked into the graph, so it can be changed without rebuilding the graph. |
| `main.py` | Orchestrates the pipeline above and writes `travel_times.csv`. |
| `plot_map.py` | Reads `travel_times.csv` and plots a world point map (Cartopy/Robinson projection), airports colored by travel time from London. |
| `h3_grid.py` | Builds a global H3 grid at a given resolution (all children of the 122 resolution-0 base cells). |
| `land_mask.py` | Classifies H3 cell centers as land or water (`global-land-mask`), so ground transport is only ever estimated where a road could plausibly exist. |
| `nearest_hub.py` | Two things: (1) `assign_travel_times` — for each grid cell, finds all hubs (airports or ports) within a search radius (haversine `BallTree`) and picks the one minimizing **total** time = the hub's own travel time from London + estimated last-mile time from the hub to the cell (ground speed for airports, sea speed for ports). Neither "nearest hub" nor "fastest hub from London" alone is correct — a farther but better-connected hub can win despite the longer last mile, and vice versa. Hubs that are themselves unreachable (`NaN` travel time) are dropped before the search, since `numpy.argmin` would otherwise silently propagate `NaN` into every result that considers them. (2) `nearest_value` — plain nearest-neighbor lookup, no hub logic, used to give each port the travel time of its nearest land cell. |
| `main_h3.py` | Splits the H3 grid into land and water cells via `land_mask.py`. Land cells get assigned via `nearest_hub.assign_travel_times` against airports. Each port then simply gets the travel time of its nearest already-computed land cell (`nearest_hub.nearest_value`) — a port isn't a separate transport mode with its own airport search, it's just a point on land that happens to also serve ships (writes `ports_travel_times.csv`). Water cells are then assigned via `nearest_hub.assign_travel_times` against those port times. Writes the combined `h3_travel_times.csv`. |
| `plot_h3_map.py` | Reads `h3_travel_times.csv` and draws the filled hex grid on the Robinson map, plus small colored dots for every airport and port (orange/magenta) so you can see which hub is driving a region's color. The color scale is capped at `COLOR_CAP_HOURS` — cells beyond that get the darkest color instead of stretching the whole scale, the same way Galton's original used discrete bands with a final "and beyond" category instead of a continuous gradient out to the true (multi-day, mid-ocean) maximum. Cells whose H3 boundary genuinely spans most of the globe (i.e. cells sitting at a pole, where all meridians converge) are dropped rather than "fixed" — treating that as an antimeridian crossing would balloon them into a giant polygon covering much of the map. |

## Running it

```bash
pipenv install
pipenv run python main.py          # -> travel_times.csv
pipenv run python plot_map.py      # -> travel_times_map.png
pipenv run python main_h3.py       # -> h3_travel_times.csv, ports_travel_times.csv
pipenv run python plot_h3_map.py   # -> h3_travel_times_map.png
```

If Cartopy fails to download coastline data with an SSL error (a known
issue with some macOS Python installs), `plot_map.py` and
`plot_h3_map.py` already point it at the `certifi` certificate bundle
instead of the system store.

## Known simplifications

- Flight time is a distance-based estimate, not real schedule data.
- Transfer time is a flat 1.5h penalty per stop, regardless of airport.
- Ground transport from an airport to a non-airport cell is a flat
  `GROUND_SPEED_KMH` (80 km/h) straight-line estimate — no roads, no
  terrain, no border crossings. This gets visibly unrealistic in places
  with no real ground infrastructure at all (e.g. Antarctica).
- Sea transport from a port to a water cell is likewise a flat
  `SEA_SPEED_KMH` (35 km/h) straight-line estimate with an effectively
  unlimited search radius, so every water cell gets a value even deep
  in the open ocean, far from the 333 ports in `ports.csv`. That's
  intentional (see MEMO.md) — the color cap in `plot_h3_map.py` is what
  keeps those multi-day mid-ocean values from swamping the map.
- `ports.csv` covers only 333 major ports (an academic benchmark
  dataset), not an exhaustive port registry.
- The route network is ~10 years old; it's used only for topology, on
  the assumption that major hub connections don't disappear quickly.
