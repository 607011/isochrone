# Isochrone Map

A modern take on Francis Galton's 1881 travel-time map: how long does it
take to reach any point in the world from London, given the global
flight network, plus a rough estimate of the "last mile" by road or sea?

## Idea

Flight *routes* (which airports connect to which) change slowly — the
big hub structure of the network is fairly stable over time, even if
individual schedules and prices are not. So this project deliberately
mixes two data sources of very different age:

- an old (~2014) OpenFlights route dataset, used only for **network
  topology** (who flies where),
- a current airport reference database, used for **coordinates**.

Flight time per route is *estimated* from great-circle distance (a rule
of thumb, not real schedules), and the fastest path from London to
every other airport is computed with Dijkstra's algorithm, including a
fixed per-connection transfer penalty. That gives every *airport* a
travel time. To turn that into a full world map, a global
[H3](https://h3geo.org/) hex grid is laid over the planet, and every
cell — land or water — is assigned the travel time of whichever
airport or port serves it fastest, including the "last mile" from that
hub to the cell itself (by road or by sea).

## Scripts

Each step is a separate module so individual pieces (e.g. the transfer
time penalty, or the flight-time formula) can be tuned without touching
the rest.

| File | Responsibility |
|---|---|
| `config.py` | All tunable constants in one place: file paths, London origin airports, flight-time formula constants, transfer time, ground/sea speed, H3 resolution, search radii, plot colormap and color cap. |
| `distance.py` | Great-circle distance between two coordinates (haversine) — `haversine_miles` (scalar) for flight-time estimation, `haversine_km_vec` (numpy-vectorized) for `friction_map_from_point.py`'s `--heli`/`--jetpack` distance-to-every-airport calculation. |
| `flight_time.py` | Rule-of-thumb flight time from distance: 30 minutes base + 1 hour per 500 miles. |
| `data_loading.py` | Reads and cleans `routes.csv` / `airports.csv`; filters to airports with a valid 3-letter IATA code and coordinates. |
| `ports_loading.py` | Reads `ports_corrected.csv` (already lon/lat-corrected, see `fix_ports_coordinates.py`) and returns the columns the rest of the pipeline needs. Deliberately thin — no `reverse_geocoder`/`pycountry` import here, so it carries no native-extension baggage. |
| `fix_ports_coordinates.py` | One-time correction script (not part of the normal pipeline): reads the raw `ports.csv`, drops rows with missing coordinates, and fixes the many rows with longitude/latitude swapped — inconsistently (some rows are fine, some aren't, no reliable pattern by value range) — detected by reverse-geocoding both possible readings of each coordinate (`reverse_geocoder`, offline) and keeping whichever one's country matches the `Country` column (`pycountry` name → ISO code, with a small override table for spellings pycountry doesn't recognize), then writes `ports_corrected.csv`. Since `ports.csv` is a static dataset that never changes, there's no reason to redo this reverse-geocoding pass on every pipeline run — run it once, commit the result, done. This also gets `reverse-geocoder` (which pulls in `cykhash`, a native Cython extension with no Windows wheel for many Python versions, requiring a working MSVC toolchain to build from source — see MEMO.md) out of the required install path entirely: it's a `[dev-packages]` entry now, only needed if you ever have to rerun this script (e.g. `ports.csv` gets updated from upstream). |
| `graph_builder.py` | Builds a directed `networkx` graph: nodes are airports, edges are direct routes weighted by estimated flight time only (no transfer time yet). |
| `travel_time.py` | Runs Dijkstra from a virtual node connected to all London airports (LHR, LGW, LCY, STN, LTN) with zero cost, so the fastest departure airport is picked automatically. Transfer time per stop is added here, not baked into the graph, so it can be changed without rebuilding the graph. `compute_shortest_times`'s origin argument can also be a `{iata: entry_hours}` dict instead of a plain list — each virtual-node edge then gets that airport's individual entry cost instead of a flat 0.0, which is how `friction_map_from_point.py` feeds in the ground time from an arbitrary starting point to each candidate departure airport. |
| `main.py` | Orchestrates the pipeline above and writes `travel_times.csv`. |
| `plot_map.py` | Reads `travel_times.csv` and plots a world point map (Cartopy/Robinson projection), airports colored by travel time from London. |
| `h3_grid.py` | Builds a global H3 grid at a given resolution (all children of the 122 resolution-0 base cells). |
| `land_mask.py` | Classifies H3 cell centers as land or water (`global-land-mask`), so ground transport is only ever estimated where a road could plausibly exist. |
| `nearest_hub.py` | Two things: (1) `assign_travel_times` — for each grid cell, finds all hubs (airports or ports) within a search radius (haversine `BallTree`) and picks the one minimizing **total** time = the hub's own travel time from London + estimated last-mile time from the hub to the cell (ground speed for airports, sea speed for ports). Neither "nearest hub" nor "fastest hub from London" alone is correct — a farther but better-connected hub can win despite the longer last mile, and vice versa. Hubs that are themselves unreachable (`NaN` travel time) are dropped before the search, since `numpy.argmin` would otherwise silently propagate `NaN` into every result that considers them. (2) `nearest_value` — plain nearest-neighbor lookup, no hub logic, used to give each port the travel time of its nearest land cell. |
| `main_h3.py` | Splits the H3 grid into land and water cells via `land_mask.py`. Land cells get assigned via `nearest_hub.assign_travel_times` against airports. Each port then simply gets the travel time of its nearest already-computed land cell (`nearest_hub.nearest_value`) — a port isn't a separate transport mode with its own airport search, it's just a point on land that happens to also serve ships (writes `ports_travel_times.csv`). Water cells are then assigned via `nearest_hub.assign_travel_times` against those port times. Writes the combined `h3_travel_times.csv`. Takes `-r`/`--resolution` (default `config.H3_RESOLUTION`) — every other script that builds an H3 grid (`map_from_airport.py`, `friction_surface_map.py`, `friction_map_from_point.py`) does too. Output filenames get a `_resN` suffix whenever a non-default resolution is used, so different resolutions don't clobber each other; `plot_h3_map.py` reads the resolution back out of the data (`h3.get_resolution`) for its title instead of trusting `config.py`, which could be stale. |
| `plot_h3_map.py` | Reads `h3_travel_times.csv` and draws the filled hex grid on the Robinson map, plus small colored dots for every airport and port (orange/magenta) so you can see which hub is driving a region's color — off by default (`--airports`/`--ports`, or `show_airports=True`/`show_ports=True`, turn each on independently). Was a single combined `--no-hubs` opt-out defaulting to shown; flipped to opt-in and split in two because plotting every airport as an identical dot is misleading when many of them (e.g. tiny Arctic strips with zero scheduled routes in `routes.csv`) contribute no actual travel-time value at all. The color scale is capped at `COLOR_CAP_HOURS` — cells beyond that get the darkest color instead of stretching the whole scale, the same way Galton's original used discrete bands with a final "and beyond" category instead of a continuous gradient out to the true (multi-day, mid-ocean) maximum. Cells whose H3 boundary genuinely spans most of the globe (i.e. cells sitting at a pole, where all meridians converge) are dropped rather than "fixed" — treating that as an antimeridian crossing would balloon them into a giant polygon covering much of the map. `origin_label` parameter controls the title/legend text, so the same function serves both the London map and `map_from_airport.py`. Output resolution is `--dpi` (or `dpi=`), default `config.MAP_DPI` — roughly quadruples in file size/render time each time you double it. `--galton` switches to Galton's original look: fixed-width discrete color bands instead of the continuous colormap, drawn as smooth `contourf` regions instead of individually colored hexagons. This is a rendering-only effect — the underlying CSV is untouched. Averaging over H3 neighbors turned out too locally-scoped to produce clean rings in noisy terrain (Sahara, Amazon interior) — the band edges just traced the noise one hex-width at a time. Instead, `_build_galton_grid()` interpolates the hex values onto a regular lat/lon raster (`GALTON_GRID_DEG`) and runs a real Gaussian blur (`GALTON_SIGMA_DEG`, `scipy.ndimage.gaussian_filter`) — land and water smoothed separately via `_nan_gaussian_filter()` so the coastline doesn't blur away — before `contourf` traces the band boundaries on that smoothed field. Also faster than the hex-neighbor approach despite doing more: a small raster + vectorized blur beats a Python loop over hundreds of thousands of hexagons. `--max-hours` overrides `GALTON_MAX_HOURS` (the color scale's total span in hours, only affects `--galton` mode — the darkest color is reached exactly at this value instead of at the fixed `COLOR_CAP_HOURS`), split evenly into `GALTON_NUM_BANDS` bands (not itself a CLI flag, since it's more about the palette's look than the scale's range); `--cmap` overrides `COLORMAP` (any matplotlib colormap name, e.g. `plasma_r`, `inferno_r`, `magma_r`, `cividis_r` — all perceptually uniform like the default `viridis_r`) and applies in both modes. `--cmap galton` is a special case: `GALTON_COLORS` is used to build a `LinearSegmentedColormap` instead of looking up a matplotlib name — ten RGB values, dark/light pairs for each of the five hues (green → yellow → pink → blue → brown), read directly off the 1881 chart by the user rather than estimated. Only the color mood is borrowed, not the original's 10-day band width — Galton's "within 10 days" category alone would cover this project's entire world (max ~48h), since travel got that much faster in 140 years. All four map-generating scripts take `--max-hours`/`--cmap`. `--labels` adds continent names (`CONTINENT_LABELS`, seven fixed hand-placed positions — these never change, so no need to derive them from a dataset, drawn bold via `CONTINENT_FONT`) and the world's most prominent cities (Natural Earth's `populated_places` layer, filtered to `SCALERANK <= CITY_LABEL_MAX_SCALERANK`, ~27 cities at the default of 0 — real city names with a genuine importance ranking, unlike our airport data, where the `name` field is an airport name like "Heathrow" rather than "London" and there's no ranking at all — drawn italic via `CITY_FONT`). No label-collision avoidance beyond that ranking filter — dense regions (e.g. Rio/São Paulo) can still overlap; an `adjustText`-style auto-declutter pass would be the next step if that becomes a problem. Coastlines and all label text use `ANTHRACITE` (`#2b2e33`) rather than gray/black, and labels no longer get a white outline stroke — closer to the crisp, dark linework of the printed 1881 original. Typography: the title is set in Playfair Display Bold (`fonts/PlayfairDisplay-Bold.ttf`, a Google Font under the OFL license — matplotlib can't address a variable font's weight axis, so this is a static Bold instance produced once with `fonttools varLib.instancer`, not the variable file itself); continents are bold Libre Baskerville, cities italic Libre Baskerville (`fonts/LibreBaskerville-Bold.ttf`/`fonts/LibreBaskerville-Italic.ttf`, same OFL license, same static-instance treatment — instantiated from Google's variable `LibreBaskerville[wght].ttf`/`LibreBaskerville-Italic[wght].ttf` at weight 700/400 respectively). Originally this used real Baskerville via matplotlib's `family="Baskerville"`, which only resolves on macOS (where it ships as a system font) — anyone running the script elsewhere silently got whatever generic serif matplotlib fell back to. Libre Baskerville is a free, OFL-licensed revival designed as a substitute for the (non-free) original, so it's bundled in the repo like Playfair Display and looks the same on every platform. Font file paths, fallback family names, and font/marker sizes all live in `config.py` (`PLAYFAIR_BOLD_PATH`, `TITLE_FONT_FALLBACK_FAMILY`, `CONTINENT_FONT_PATH`, `CITY_FONT_PATH`, `CONTINENT_FONT_FALLBACK_FAMILY`, `CITY_FONT_FALLBACK_FAMILY`, `TITLE_FONT_SIZE`, `CONTINENT_FONT_SIZE`, `CITY_FONT_SIZE`, `CITY_MARKER_SIZE`) rather than as literals scattered across `ax.text()`/`ax.set_title()` calls, so the look can be tuned without touching the rendering code; if a font file is ever missing, each falls back to a generic `serif` family rather than erroring. Avoid Greek letters or other glyphs a display font might not cover in title text — Playfair Display has no `σ`, which silently renders as a tofu box instead of erroring. **Projection**: Mercator is the default (matching Galton's original, and the reason Greenland/Antarctica look oversized — a real Mercator distortion, not a bug), clipped to ±85° latitude since Mercator can't represent the poles (infinite distance) — or, under `--galton`, clipped to the original chart's own asymmetric 80°N/60°S crop instead of the generic symmetric one. Pass `--robinson` for the earlier equal-area-ish Robinson projection instead. `--grid` draws a longitude/latitude graticule every 20° (`GRID_STEP_DEG`) via `ax.gridlines()`, in the same anthracite color and line width (`COASTLINE_LINEWIDTH`) as the coastlines (at 80% opacity, like the airport/port dots, so it stays subtle), so it reads as part of the same linework rather than a separate technical overlay. Under `--galton`, two more of the original's frame elements appear regardless of `--grid`: bare-number degree labels on all four sides (cartopy's gridliner `draw_labels` with a `FuncFormatter` stripping the default °/N/E/S/W suffix, only supported for rectangular projections — so this is skipped under `--robinson`) and a double border line around the map (the existing "geo" spine plus a second `Rectangle`, `FRAME_GAP_PT` apart from it). That gap is computed in points via the axes' pixel bounding box (`ax.get_window_extent()`), not as a fixed fraction of `ax.transAxes` — the map isn't square, so a fractional inset would leave visibly different horizontal/vertical gaps; going through points keeps the two rules the same distance apart on both axes, like the original's tight double ruling. The internal graticule lines themselves still only draw when `--grid` is also passed — `alpha=0` hides them while leaving the label ticks in place — so `--galton` alone gets the frame and axis numbers without the busier internal grid. `--title` shows the title (off by default, so the map's degree labels/legend aren't competing with a headline); the whole PNG background (everything outside the map panel — title area, legend, colorbar margins) is filled with `BACKGROUND_COLOR` (`#dad4bb`, a warm aged-paper tan roughly between the two reference RGB values the user gave), applied via both `fig.patch.set_facecolor()` and `savefig(..., facecolor=...)` since `bbox_inches="tight"` re-renders at save time. The legend's origin-star marker is rendered at `s=200` on the map (deliberately eye-catching) but shown at a quarter of that area (`handle.set_sizes(handle.get_sizes() / 4)`, applied after `ax.legend()` to just that one handle) — `s` is an area, so dividing by 4 rather than 2 is what actually makes the star look half as big, not just a quarter smaller. Under `--galton`, the legend text switches to Playfair Display too, matching the title. **Color legend** (`--galton` only): instead of the continuous colorbar (which the non-`--galton` path still uses unchanged), `_draw_galton_color_legend()` draws a single compact line in the style of the 1881 original's own legend — "Explanation of colours." followed by one small color swatch + hour range per band ("0-8h.", "8-16h.", ..., "mehr als 48h." for the open-ended top band, since `extend="max"` already gives everything past the last boundary the same color), then "Published by heise Medien, 2026." in italic underneath — instead of a gradient bar with a separate axis-label row below it, which took up noticeably more vertical space and doesn't match how Galton's own chart presented its five categories (as discrete swatches with names, not a ramp). Positioned in figure coordinates rather than `ax.transAxes`, since the legend sits below the map axes, outside its own bounding box; x-positions are accumulated from the actually-rendered width of each text/swatch (`fig.canvas.draw()` + `get_window_extent()`, the same trick already used for the double-border gap) rather than estimated in advance, since text width depends on font/size in ways that aren't known until render time. Swatch colors come directly from `GALTON10_COLORS` for `--cmap galton10`, or are sampled from the interpolated colormap at each band's midpoint otherwise; swatches get a sketch-wobbled border (`_sketch()`) like the rest of the retro linework. Sizes/spacing live in `config.py` (`GALTON_LEGEND_FONT_SIZE`, `GALTON_LEGEND_SWATCH_WIDTH_PT`/`_HEIGHT_PT`, `GALTON_LEGEND_GAP_PT`). `--cmap galton10` is a fixed-palette alternative to `--cmap galton`: instead of interpolating `GALTON_COLORS` into a continuous `LinearSegmentedColormap`, it builds a `ListedColormap` from the same ten RGB values (`GALTON10_COLORS`, identical to `GALTON_COLORS`) — one solid color per step, no interpolation. It's just a colormap choice like any other `--cmap` value, so it also works without `--galton` (each hexagon gets whichever of the ten colors its value falls into); combined with `--galton`, the ten colors always split `--max-hours` into exactly ten equal-width bands instead of `GALTON_NUM_BANDS`, since `contourf` needs as many boundaries as the colormap has colors. Filenames now distinguish the two: `_galton10` instead of `_galton` when `cmap_name == "galton10"`, since they used to collide (any `--cmap` value used to leave the filename unaffected) and silently overwrite each other's output. `GALTON_NUM_BANDS` defaults to 6, not more — with `--cmap galton`, more/narrower bands oversample the ten anchor colors closely enough that the interpolated palette starts looking like the flat `galton10` one instead of the smoothly-blended five-hue-family look; 6 bands (8h wide each, at the default `GALTON_MAX_HOURS` of 48) is wide enough to read as distinct color families again. `--lat-limits=NORTH,SOUTH` (e.g. `--lat-limits=80,-60`) overrides the Mercator crop directly instead of picking between the two built-in defaults (85/-85, or 80/-60 under `--galton`); has no effect under `--robinson`, which always shows the full globe. `origin_points` is a new `plot_h3_map()` parameter (a list of `(lat, lon)` pairs) for origins that aren't airports — `friction_map_from_point.py` uses it to place the star at the actual start coordinates instead of looking one up in `travel_times.csv` by IATA code; existing callers are unaffected since it defaults to `None`, falling back to the original `origin_iatas` lookup. `--rivers` adds Natural Earth's `RIVERS` layer (`cfeature.RIVERS`, 110m scale — only the world's major rivers, matching how sparingly Galton's original draws them), in the same anthracite color and `COASTLINE_LINEWIDTH` as the coastlines, drawn at the same `zorder` right after them. `--galton-sigma` overrides `GALTON_SIGMA_DEG` (default 3.0°, the Gaussian blur's standard deviation in `_build_galton_grid()`) — larger softens/blurs the bands further, smaller keeps them closer to the raw per-cell noise; only affects `--galton` mode, same as `--max-hours`. **Performance**: the non-`--galton` hexagon `PolyCollection` used to pass `transform=ccrs.PlateCarree()` straight through to matplotlib, which makes cartopy reproject every polygon individually via its generic (Shapely/GEOS-based) geometry-tracing path — profiling a default-settings render showed this ate 96% of a 215-second total. `_project_polygons()` instead projects every cell's vertices in a single vectorized `ax.projection.transform_points()` call and builds the `PolyCollection` already in projected coordinates (no `transform=` needed, since that's the axes' native data space) — same output, ~4 seconds instead of ~215. Verified against the antimeridian region (Fiji/date line) under both Mercator and Robinson to confirm no wraparound artifacts from skipping cartopy's dedicated antimeridian-splitting logic — H3 cells are small and already antimeridian-corrected in `_cell_polygon_lonlat()`, so the generic per-geometry path wasn't buying anything for this use case. **Retro look** (`--galton` only): coastlines, rivers, the graticule, the double border, and the colorbar's dividers/outline no longer render as geometrically perfect paths — `_sketch()` calls each artist's built-in `set_sketch_params()` (the same mechanism behind `plt.xkcd()`, here applied per-artist instead of globally via `rcParams`) so they wobble slightly, like hand-engraved copperplate lines instead of a digitally traced vector outline. `config.RETRO_SKETCH_RANDOMNESS` matters as much as the amplitude (`RETRO_SKETCH_SCALE`): matplotlib's sketch filter is a perturbed sine wave, and a low randomness (its own default is 16) makes that read as a smooth, regular ripple rather than an irregular hand-tremor — pushing randomness up and scale down (`0.05`/`15`/`10`, calibrated by eye at the project's normal render scale — even the initial retuning to `0.3` still read as too strong once seen at full size) is what makes it look like jitter instead of a wave. Not exposed as CLI flags since they're a fixed part of the look, not something to tune per-map. Cartopy's `Gridliner` needed a workaround: `gl.set_sketch_params()` sets it on the `Gridliner` container itself, but the meridian/parallel lines it actually draws are separate internal `LineCollection` artists (`gl.xline_artists`/`gl.yline_artists`) that don't exist until the first `fig.canvas.draw()` call — so the sketch has to be applied to those directly, after that draw (reusing the one already needed to measure the double-border's pixel gap), not to `gl` itself. The gridline degree labels are set to `CITY_FONT` (the same italic Libre Baskerville as city labels) rather than the matplotlib default, so the small numeric annotations on the map read as one consistent typeface. Separately, `_apply_retro_noise()` re-opens the already-saved PNG after `fig.savefig()` and adds a synthetic paper-grain texture (`config.RETRO_NOISE_STRENGTH`) — a coarse, upscaled noise field for blotchy foxing-like mottling blended with fine per-pixel noise for grain, added to all three RGB channels and clipped back to 0-255. Doing this as post-processing on the finished raster (rather than, say, a textured background patch under the map) is simpler and resolution/projection-independent, and covers the whole image (map, legend, colorbar) uniformly. |
| `map_from_airport.py` | Reruns the exact same pipeline (flight graph → Dijkstra → H3 land/sea assignment → plot) from an arbitrary airport instead of London. Usage: `pipenv run python map_from_airport.py <IATA>`. All outputs are saved under a filename slug built from the IATA code and airport name. `build_sea()` (ports + water cells from an already-computed land layer) is factored out so `friction_map_from_point.py` can reuse it with a different land layer. |
| `friction_surface_demo.py` | Standalone regional comparison, not part of the main pipeline: downloads/filters a real OpenStreetMap road network (Queensland extract via Geofabrik, filtered with `pyrosm` to a box around Birdsville) and computes real road-network travel time from Birdsville Airport via Dijkstra, alongside the same flat-speed isotropic model the main pipeline uses. Renders both side by side. |
| `friction_surface_global.py` | The regional idea above, but global, using a pre-computed friction raster instead of live routing (see "Anisotropic ground transport" below). Three steps, each cached to disk: (1) downsample the 1km MAP friction raster to ~11km via min-pooling (so thin fast roads survive the downsampling instead of being averaged away), (2) mask to land only (`global-land-mask` — the raw raster also has slow-but-finite values over open ocean, presumably for ferries, which would otherwise let "ground" paths shortcut across water) and build an ~1.5M-node graph over the remaining land pixels (8-neighbour, edge weight = friction × real great-circle distance between pixel centers), (3) add a virtual super-node connected to each airport's nearest pixel with edge weight = that airport's own travel time from its origin, then run a single `scipy.sparse.csgraph.dijkstra` from it — the same virtual-origin trick as `travel_time.py`/`nearest_hub.py`, just over a raster graph instead of a radius search, so it directly yields flight time + real anisotropic ground time combined. The graph itself (steps 1-2) doesn't depend on the origin, only step 3's edge weights do — `load_graph()` reloads the cached graph so a different origin only needs to rerun Dijkstra, not rebuild everything. |
| `friction_surface_map.py` | The London-specific entry point: maps each global H3 land cell to its nearest node in the friction graph's result (computed for London by `friction_surface_global.py`'s `main()`), keeps the existing sea cells from `h3_travel_times.csv` unchanged, and renders the combined map. |
| `friction_map_from_point.py` | The friction-surface ground model (`friction_surface_global.py`) from an arbitrary land point (`lat lon`) instead of London — e.g. `pipenv run python friction_map_from_point.py 48.85 2.35 --label "Paris (point)"`. Supersedes and replaces the earlier airport-only `friction_map_from_airport.py` (removed): passing an airport's own coordinates here reproduces its output bit-for-bit (verified numerically — max difference across 2M+ H3 cells was floating-point noise, ~1e-14h), since an airport is just a point too. `build_friction_land()` now lives here directly. Reverses the direction of the friction-surface Dijkstra: instead of spreading ground time out from every airport (its own travel time from London is already known), a single Dijkstra runs *from* the chosen point across the same cached land graph *to* every airport pixel, giving that airport's individual ground time from the point. Those (no longer uniform) ground times become the virtual-origin edge weights in `travel_time.compute_shortest_times`, so the normal flight-network Dijkstra folds "ground time to the airport" and "flight + transfer time" into one shortest-path run — same super-source trick used everywhere else in this project, just with the source and sink roles swapped relative to `friction_surface_global.py`. Airports with no land connection to the point (e.g. across open water the friction graph doesn't route over) simply get infinite ground time and drop out of the candidate set on their own. From there `build_friction_land()` runs again, in its original direction (airport → world), to spread ground time back out across every land H3 cell. The origin marker is plotted directly at the given coordinates (`plot_h3_map`'s new `origin_points` parameter) rather than looked up by IATA code, since the start isn't an airport. `--heli`/`--jetpack` add a faster-but-range-limited way to reach each candidate departure airport (and, further below, every H3 tile directly): straight-line (haversine) distance at a fixed speed (`HELI_SPEED_KMH`/`JETPACK_SPEED_KMH` in `config.py`) instead of the friction-graph route, but only within `HELI_RANGE_KM`/`JETPACK_RANGE_KM` — beyond that a given point simply isn't reachable that way. `_air_hours_to()` computes this vectorized (`haversine_km_vec()`, `distance.py`) against any set of destination coordinates. Passing both flags together (or `--james-bond` as shorthand for `--heli --jetpack`) chains them: heli for the first `HELI_RANGE_KM`, jetpack for up to another `JETPACK_RANGE_KM` beyond that. `-v`/`--verbose` (this script only) prints a one-time config overview before any work starts (origin, resolution/dpi, projection, `--galton` settings, active overlays, heli/jetpack speeds/ranges) plus a progress message before each major step (loading data, the combo-Dijkstra, spreading ground time to land cells, building sea cells, writing the CSVs, drawing the map) — without it, the script stays as quiet as before (just the friction-graph Dijkstra timing and the final "Karte gespeichert unter" line, both unconditional and unrelated to this flag).

Naively taking `min(ground_time_from_origin, air_time)` per destination is wrong, though — it either uses the friction graph for the *entire* trip or air travel for the *entire* trip, with no way to combine them, so it silently discards the flight distance the moment the destination is even slightly outside heli/jetpack range and forces the whole remaining trip to be walked from the origin (not from the edge of the flight range). `_combo_ground_minutes()` fixes this properly, reusing the same virtual-super-source Dijkstra trick used throughout this project (e.g. `friction_surface_global.py`'s airport-seeded world Dijkstra): every friction-graph node within air range gets a virtual edge from the origin weighted by *that node's own* `_air_hours_to()` value, then a single Dijkstra over the whole land graph gives, for every point in the world, the minimum over all reachable "landing spots" of (flight time to that spot + ground time from there onward) — genuinely "fly as far as is worthwhile, then walk the rest," radially symmetric around the flight-range circle instead of only showing up in whichever direction happened to make pure at-the-origin walking competitive. The origin itself is always a zero-cost landing spot, so this single function also covers plain walking with no flight at all — no special-casing needed for runs without `--heli`/`--jetpack`. `build_travel_times_from_point()` uses its result directly as each airport's entry time (replacing the old separate `min(ground, air)` computation entirely), and `_apply_combo_ground_to_h3()` applies the same array to every H3 land tile. `_apply_air_reach_to_h3()` (pure air time, no walking) still runs separately and additionally, since it's the only thing that can color H3 *sea* tiles — the friction graph is land-only. `air_suffix` (`_heli`/`_jetpack`/`_bond`) is threaded through every output filename, including the CSVs (not just the PNG) — otherwise a `--heli` run's `travel_times_from_<slug>.csv` would silently overwrite the plain run's, the same class of collision fixed earlier for `--cmap galton`/`galton10`. |

## Running it

```bash
pipenv install
pipenv run python main.py                 # -> travel_times.csv
pipenv run python plot_map.py             # -> travel_times_map_london_airports_points.png
pipenv run python main_h3.py              # -> h3_travel_times.csv, ports_travel_times.csv
pipenv run python plot_h3_map.py          # -> h3_travel_times_map_london_h3_land_and_sea.png
pipenv run python map_from_airport.py BVI # -> same outputs, from Birdsville instead of London
```

If Cartopy fails to download coastline data with an SSL error (a known
issue with some macOS Python installs), `plot_map.py` and
`plot_h3_map.py` already point it at the `certifi` certificate bundle
instead of the system store.

For `friction_surface_demo.py`, first download the road network extract
(not committed, ~196 MB):

```bash
mkdir -p osm_data
curl -L -o osm_data/queensland-latest.osm.pbf \
  https://download.geofabrik.de/australia-oceania/australia/queensland-latest.osm.pbf
pipenv run python friction_surface_demo.py
```

The Overpass API (which the more common `osmnx.graph_from_point()`
approach uses to fetch road data on demand) was unreachable from this
project's dev environment — direct HTTPS downloads worked fine, live
Overpass queries didn't (connection refused / 406, even via `curl`, on
multiple mirrors). That's why this script reads a pre-downloaded
Geofabrik `.osm.pbf` extract via `pyrosm` instead of querying Overpass
live; worth trying `osmnx` directly first in an environment where
Overpass is reachable.

For the global anisotropic map (`friction_surface_global.py` /
`friction_surface_map.py`), download the friction surface first
(not committed, ~744 MB unzipped):

```bash
mkdir -p friction_data
curl -L -o friction_data/friction_surface.zip \
  "https://data.malariaatlas.org/geoserver/ows?service=CSW&version=2.0.1&request=DirectDownload&ResourceId=Explorer:2020_motorized_friction_surface"
unzip -o friction_data/friction_surface.zip -d friction_data
pipenv run python friction_surface_global.py  # ~1-2 minutes, caches intermediate results
pipenv run python friction_surface_map.py     # -> h3_travel_times_map_london_friction_surface_land.png
```

## Known simplifications

- Flight time is a distance-based estimate, not real schedule data.
- Transfer time is a flat 1.5h penalty per stop, regardless of airport.
- The main pipeline's (`main_h3.py`) ground transport from an airport to
  a non-airport cell is a flat `GROUND_SPEED_KMH` (80 km/h) straight-line
  estimate — no roads, no terrain, no border crossings. It's *isotropic*:
  the model assumes you can travel equally fast in every direction from
  an airport, when real ground transport obviously follows roads/rail
  (compare the historical
  [Melbourne 1920s tram/rail isochrone map](https://en.wikipedia.org/wiki/Isochrone_map)
  that inspired this observation). Two separate scripts demonstrate the
  anisotropic alternative instead of changing the main pipeline outright
  (see `MEMO.md` for why they stayed separate):
  - `friction_surface_demo.py` — one region (Birdsville, Australia)
    using a real OpenStreetMap road network.
  - `friction_surface_global.py` / `friction_surface_map.py` — the whole
    world, using a pre-computed friction raster (Malaria Atlas Project)
    and a cost-distance graph instead of live routing. Doesn't cover
    Antarctica (the raster stops at 60°S) — those cells fall back to
    whatever the nearest available friction-graph node happens to be,
    which is visibly wrong the same way the isotropic model's Antarctica
    values were.
- Sea transport from a port to a water cell is likewise a flat
  `SEA_SPEED_KMH` (35 km/h) straight-line estimate with an effectively
  unlimited search radius, so every water cell gets a value even deep
  in the open ocean, far from the 333 ports in `ports.csv`. That's
  intentional (see MEMO.md) — the color cap in `plot_h3_map.py` is what
  keeps those multi-day mid-ocean values from swamping the map. The
  friction-surface map keeps this same sea model unchanged; only land
  cells get the anisotropic treatment.
- `ports.csv` covers only 333 major ports (an academic benchmark
  dataset), not an exhaustive port registry.
- The route network is ~10 years old; it's used only for topology, on
  the assumption that major hub connections don't disappear quickly.
